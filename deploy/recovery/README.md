# Проверка восстановления на Mac

Это отдельные инструменты доверенного компьютера, не установка/обновление VPS. Нужен Docker Desktop для Mac; системного Python 3.9 достаточно только для распаковки исходников. Python 3.12/cryptography и Docker CLI выполняются в отдельном образе. Вендорные колёса рассчитаны на linux/amd64, поэтому Apple Silicon использует эмуляцию; производительность проверяется при фактическом запуске на Mac.

Запуск из проверенных неизменяемых исходников:

```bash
bash deploy/recovery/recover-mac.sh SHA256_СКАЧАННОЙ_КОПИИ_ИЗ_ЛК
```

Окна выбора по очереди запрашивают .encrypted и закрытый recovery-ключ. Не выбирать SSH-ключ или ключ подписи. Файлы должны находиться вне каталога исходников (не входят в контекст сборки), их содержимое не печатается. SHA-256 проверяется до сборки и работы с ключом. Исходные файл/ключ монтируются read-only, без передачи на VPS/GitHub.

Launcher явно выбирает context desktop-linux, отвергает удалённый endpoint и требует OperatingSystem Docker Desktop. Системные настройки Docker не меняются. Во время сборки/предварительного pull скачиваются только закреплённые публичные образы. Зависимости устанавливаются offline с проверкой хэшей из колёс. Во время восстановления контейнер проверяющего процесса и PostgreSQL работают без сети. Docker socket передаётся только проверяющему процессу, чтобы создавать/удалять собственный временный PostgreSQL; ключи ему доступны только для чтения. Временная БД не получает Docker socket, порты, рабочие тома или ключ.

Расшифровка/распаковка происходит в закрытом временном tmpfs. Полностью проверяются AEAD, manifest файлов, извлечение config/documents, реальное pg_restore и количество строк по каждой таблице. Только после успеха создаётся JSON-подтверждение в Documents/ArmadaRecoveryReceipts. При штатном завершении временная БД/расшифрованные файлы удаляются. Исходные архив/ключ и публичные образы остаются. Лимиты памяти и временного пространства рассчитаны на первую небольшую копию; большие архивы требуют отдельного расчёта ресурсов.

На синтетической зашифрованной копии реальный запуск этого образа с Docker CLI/сокетом, read-only входами и сетью none выполнил PostgreSQL 17 restore, проверку строк и извлечённых файлов. Отрицательная копия с неверным числом строк отвергнута без receipt. Логи: /workspace/armada-recovery-check/contained-test.log. Первоначальная ошибка тестовой обвязки чтения root-owned receipt на хосте исправлена чтением через read-only контейнер, восстановитель не менялся.

Три исполняемых проверки launcher (с подменёнными командами Mac/Desktop): удалённый endpoint отклоняется до сборки, неверный SHA-256 отклоняется до сборки, допустимый путь сохраняет offline/read-only параметры и исходные файлы. Команда: python3 tests/check_recovery_launcher.py. bash -n и git diff --check — OK.

Фактический Mac/Apple Silicon и реальная пользовательская копия ещё не проверены. Подтверждение успешной передачи на Диск не объявляется проверкой восстановления. Подписанный выпуск 6.31.0 не изменяется; эти средства распространяются отдельно.

## Диагностика реального запуска на Mac

На Mac владельца исходные образы сначала не скачивались с ошибкой TLS bad record MAC; отдельные pull с проверкой TLS прошли. Затем инструмент собран, PostgreSQL скачан, но проверка реального архива завершилась общим отказом без receipt. Причина пока не установлена. Добавлен check.py — диагностический вход поверх неизменённого verify_backup: фиксированные фазы Docker, код/тип ошибки и имена функций без исходного текста, приватных сообщений, SQL, stderr, аргументов и ключей. Диагностический вход проверен в ранее построенном контейнере через read-only bind файла: положительное восстановление и отрицательная проверка числа строк прошли. Три теста tests/check_recovery_diagnostics.py проверяют отсутствие секретных значений исключений/stderr/аргументов в выводе и делегирование успеха. Это подготовка безопасного уточнения причины; реальная копия на Mac ещё не признана восстановленной.
