# Beget: размещение приложения и перенос с NAS

Сборка подготовлена для Ubuntu 24.04, 2 CPU / 2 ГБ RAM / 20 ГБ диска. Это инструкция установки, не подтверждение выполненного развёртывания. Сервер: 31.129.102.126. Публичная часть: armada-sibir.ru и www.armada-sibir.ru; ЛК: app.armada-sibir.ru.

## Подготовка

Подключение с Mac, где хранится ваш ключ:

```sh
ssh-add ~/.ssh/armada_beget
ssh -o IdentitiesOnly=yes -o ServerAliveInterval=30 -i ~/.ssh/armada_beget root@31.129.102.126
```

Система уже обновлялась. Следующий шаг — установить Docker, если он ещё не установлен:

```sh
apt install -y docker.io docker-compose-v2
systemctl enable --now docker
docker compose version
```

Смените первоначальный пароль root командой `passwd`, если ещё не сделали: он ранее попал на скриншот. Не передавайте приватный SSH-ключ и парольную фразу в чат. Отключать вход по паролю можно только после проверки нового независимого входа по ключу и доступности консоли Beget.

Загрузите архив 6.14, распакуйте исходники, например в `/opt/armada`. Не помещайте резервные копии в каталог публичного сайта. Скопируйте `deploy/beget/.env.example` в `deploy/beget/.env`, укажите существующий контролируемый адрес TLS_EMAIL. Сам файл не содержит паролей приложения. Соберите образы:

```sh
cd /opt/armada
docker compose -f deploy/beget/compose.yml build
```

Образы приложения собираются из включённых Python-колёс; базовые Docker-образы скачиваются отдельно. Следите за свободным диском `df -h`: 20 ГБ — небольшой запас для образов, документов и копий.

## Сначала выбрать: перенос или пустая установка

**Для текущей АРМАДЫ нужен перенос существующей базы**, чтобы сохранить пользователей, ФИО, пароли, права и документы. Не создавайте руководителей заново и не запускайте очистку.

1. На NAS остановите запись в приложение (`web` и почтовый обработчик, если он есть), оставив PostgreSQL работающим. Снимите согласованный `pg_dump -Fc --no-owner --no-acl` базы `armada`, архив тома конфигурации и архив документов. Используйте реальные имена томов проекта `armada-test`; сначала проверьте `docker compose -p armada-test config` и `docker volume ls`. Не угадывайте пути и не удаляйте тома.
2. Скопируйте эти приватные архивы на VPS через SSH/SCP с Mac. Права каталога 700, файлов 600. Сохраните NAS и исходную копию для возврата. Секреты не вставляйте в чат.
3. **До первого запуска PostgreSQL на VPS** восстановите прежний том `config`: `django-key`, `database-url`, оба postgres-пароля и `mail-key`, если он уже был. Не смешивайте секреты разных установок. При отсутствии старого `mail-key` инициализатор создаст его; это безопасно только если в старой базе ещё нет зашифрованных почтовых паролей.
4. Восстановите документы в том `documents` и права владельца 10001:10001. Встроенный сервис `init` монтирует config и documents с записью; его можно использовать для распаковки с `--entrypoint tar`. У web конфигурация доступна только для чтения.
5. Запустите `init` и `db`, проверьте готовность базы. Убедитесь, что целевая база **пустая**. Восстановление ниже предназначено только для свежей целевой базы, не для перезаписи существующих данных:

```sh
docker compose -f deploy/beget/compose.yml up -d init db
docker compose -f deploy/beget/compose.yml exec -T db pg_isready -U armada_admin -d armada
# На свежей базе: передайте сохранённый database.dump через stdin.
docker compose -f deploy/beget/compose.yml exec -T db pg_restore \
  -U armada_admin --role=armada_app -d armada --no-owner --no-acl < /PRIVATE/PATH/database.dump
```

`/PRIVATE/PATH/database.dump` заменяется реальным приватным путём. Роль `armada_app` обязательна: иначе таблицы могут оказаться у другого владельца и миграции не выполнятся. При любой ошибке восстановления не запускайте рабочий сайт до её устранения.

6. Запустите `web mailworker`, дождитесь healthy, проверьте вход прежних руководителей, количество записей и открытие прежних документов. Миграции добавляют новые таблицы без удаления данных. Команду создания руководителей для восстановленной базы не запускайте.

Для действительно пустой установки можно запустить init/db/web и выполнить штатное первоначальное создание руководителей по действующей инструкции проекта; это другой сценарий, не перенос.

## DNS и HTTPS

После готовности приложения измените только A-записи корня, www и app на 31.129.102.126. MX, SPF, DKIM и остальные почтовые записи сохраняются. Не добавляйте AAAA без настроенного IPv6. Публичный IP VPS не является адресом почтового сервера Beget.

Откройте входящие TCP 80 и 443, сохранив доступ SSH 22. Только после проверки SSH можно включать UFW с этими разрешениями. PostgreSQL, web:8000 и старый NAS:18080 в интернет не публикуются.

```sh
docker compose -f deploy/beget/compose.yml up -d
docker compose -f deploy/beget/compose.yml ps
docker compose -f deploy/beget/compose.yml logs --tail=80 web mailworker proxy
```

Caddy получает сертификаты автоматически после обновления DNS и доступности портов. До этого не обещается рабочий HTTPS. Сертификаты сохраняются в отдельных томах. `SECURE_*` настройки включены, прокси передаёт HTTPS-признак; прямого публичного порта web нет.

NAS после переноса можно использовать для закрытых резервных копий. Не оставляйте два независимо изменяемых рабочих экземпляра. Переключение обратно на старую базу теряет изменения, сделанные после переноса: перед возвратом нужна актуальная согласованная копия.

## Почта

Создайте настоящие ящики в Beget и проверьте доступность IMAP/SMTP на вашем тарифе. В `.env` укажите подтверждённые провайдером серверы/порты; TLS-проверка сертификатов обязательна. Руководитель связывает ящики с сотрудниками в ЛК. Работают два руководителя с доступом ко всем подключённым ящикам; обычный сотрудник видит только свои.

Автоматическое создание/удаление ящиков у Beget через API не реализовано. Отметка «Нужна почта» создаёт заявку, затем ящик создаётся в панели провайдера. Пароль панели Beget и пароль сервера для подключения почты не подходят. IMAP/SMTP на реальных ящиках перед вводом в эксплуатацию ещё нужно проверить.

## Резервные копии

```sh
bash deploy/beget/backup.sh
```

Скрипт временно останавливает web/почтовый обработчик, снимает базу, конфигурацию и документы, проверяет читаемость дампа и контрольные суммы, возобновляет приложение. Результат по умолчанию `/var/backups/armada/armada-<UTC>.tar.gz`. Конфигурация содержит секреты: храните архив приватно. **Без mail-key из той же конфигурации зашифрованные почтовые пароли не восстановятся.**

Расписание ещё не включено: это нужно сделать отдельно после проверки первой копии и внешнего хранилища. Переносите копии на NAS/другое хранилище; копия на том же VPS не защищает от потери VPS. Автоматического удаления старых копий нет — на 20 ГБ контролируйте место и согласуйте срок хранения. При восстановлении используйте пустую целевую базу и согласованные config+documents+database из одного архива. Работоспособность этого формата проверена на отдельном тестовом проекте с восстановлением базы и зашифрованного пароля.
