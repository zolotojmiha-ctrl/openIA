# Тест на Synology

Только для проверки в домашней сети, без настоящих документов, телефонов и паролей компании. Домен и роутер не меняются. Адрес NAS: `192.168.50.248`. Приложение публикует единственный порт `18080`, привязанный к этому адресу. База данных не имеет опубликованных портов. При изменении адреса NAS нужно обновить значение NAS_IP в compose либо задать переменную окружения.

## Что устанавливается

Проект `armada-test`: контейнер подготовки секретов (`init`, после успешного выполнения остановлен — это нормально), база (`db`) и приложение (`web`). Приложение запускается без административных прав, с файловой системой только для чтения. Создаются только два собственных Docker-тома проекта: `config` с ключами и `database` с тестовой БД. Не подключаются папки `photo`, `homes`, `Наша семья`, весь том NAS или Docker socket. Существующие контейнеры не меняются. Память web ограничена 512 МБ, db 384 МБ, init 128 МБ. Перед запуском проверить свободную память NAS; отдельная копия фотографий всё равно нужна для защиты от аппаратного сбоя.

## Установка через интерфейс DSM

1. Скачать ZIP ветки `feature/accounts-foundation` через GitHub.
2. Загрузить его в созданную папку `docker/armada-test`, распаковать. Найти корневую папку распакованного проекта: внутри должны быть `docker-compose.yml`, `requirements.txt`, папки `server`, `portal`, `deploy`.
3. В Container Manager → «Проект» → «Создать» указать имя `armada-test` и путь к этой корневой папке. Выбрать существующий YAML, указать `docker-compose.yml`.
4. Запустить сборку и проект. На NAS первая загрузка образов и установка зависимостей могут занять время. `init` должен завершиться с кодом 0, db и web — стать исправными. Если сборка завершается ошибкой, прислать текст ошибки без секретов; не удалять существующие образы и контейнеры для освобождения места.
5. В браузере компьютера из той же домашней сети открыть `http://192.168.50.248:18080/cabinet/login/`.

На первом запуске пользователей нет. Сайт при этом открывается, а войти ещё нельзя. База и ключи сохраняются между перезапусками. Не включать маршрутизацию портов, UPnP и внешнюю публикацию этого HTTP-режима.

## Учётные записи двух руководителей

В Container Manager открыть контейнер `web` именно проекта `armada-test`, затем терминал `/bin/sh`. Выполнить:

```sh
python server/manage.py bootstrap_leaders
```

Учётные записи не входят в архив и не создаются автоматически. Введите выбранные вами имена и два разных телефона. Для проверки в домашней сети используйте вымышленные данные. Придумайте два разных временных пароля от 6 символов; они вводятся скрыто, не отображаются и не нужны в переписке. После первого входа каждый пароль необходимо сменить. Пароли действуют 24 часа. Если терминал не поддерживает скрытый интерактивный ввод, остановиться и сообщить — не помещать пароли в YAML или командную строку.

## Что проверить

- Вход каждым руководителем и обязательная смена временного пароля.
- Создание тестового сотрудника, выдача прав, вход сотрудником.
- Сотрудник не открывает управление пользователями, в том числе по прямой ссылке.
- Блокировка и изменение прав завершают старый сеанс сотрудника.
- Перезапуск только проекта `armada-test` сохраняет пользователей и настройки.
- `/portal/` остаётся отдельной демонстрацией; рабочие документы подключены в версии 3.0.0, офлайн-дефекты остаются следующим этапом. См. [DOCUMENTS.md](DOCUMENTS.md).

HTTP здесь используется только для локального теста. Даже дома он не шифрует ввод. Для настоящих данных и внешнего доступа нужна отдельная настройка HTTPS, резервирования и восстановления. Режим LAN_TEST принимает только конкретные локальные IPv4-адреса, не домены и не `*`; он не заменяет правила роутера и сетевой экран.

## Остановка и сохранность данных

В интерфейсе Container Manager остановить только проект `armada-test`. Не удалять тома `config` и `database`: они нужны для повторного запуска. Никогда не запускать общую очистку Docker или команду удаления всех томов. Если были удалены ключи при сохранённой БД, автоматически новые пароли БД не подойдут к прежней БД: требуется восстановить конфигурацию из копии либо отдельно осознанно пересоздать только тестовую установку.

Зависимости для Python 3.12 и Linux x86_64 включены в `deploy/synology/wheels/` вместе с SHA-256. При сборке pip проверяет хеши и не обращается в интернет. Docker всё равно должен скачать базовые образы Python и PostgreSQL. Пакет предназначен для DS720+/DS723+ (x86_64), не для ARM-моделей Synology.

## Совместимость с ядром DSM

В конфигурации не задаются `cpus` (NanoCPUs/CFS) и `pids_limit`: на части Synology эти возможности ядра отсутствуют. Ограничения памяти сохранены. Это не требует обновления DSM, удаления существующих контейнеров или очистки томов. После ошибки создания заменить только `docker-compose.yml` в той же папке и повторить сборку того же проекта. Томам проекта оставить прежние имена.
