# Рабочие учётные записи: этап 1

Состояние: реализованы серверный вход по телефону и паролю, два равноправных руководителя, индивидуальные права сотрудников, создание/редактирование/блокировка сотрудников, сброс их паролей, принудительная первая смена пароля, завершение старых сеансов и журнал действий. Это отдельное приложение `/cabinet/`; `/portal/` остаётся небезопасной демонстрацией.

Настоящие аккаунты не созданы. Рабочее приложение не опубликовано. GitHub Pages не запускает Python, базу данных или серверную авторизацию; существующая ветка `demo-preview` остаётся только демонстрацией.

## Локальная разработка

Из корня репозитория, Python 3.12:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
ARMADA_DEVELOPMENT=1 .venv/bin/python server/manage.py migrate
ARMADA_DEVELOPMENT=1 .venv/bin/python server/manage.py runserver 127.0.0.1:8020
```

Команды повторяемы. Используется SQLite только для локальной разработки. `.runtime/` содержит локальную базу и автоматически созданный ключ: каталог исключён из Git. Не раздавать корень проекта обычным HTTP-сервером: в нём расположены приватные служебные файлы. Django выдаёт только явно разрешённые публичные файлы и маршруты.

## Первые два руководителя

Только в закрытом интерактивном терминале:

```sh
ARMADA_DEVELOPMENT=1 .venv/bin/python server/manage.py bootstrap_leaders
```

Команда запрашивает скрытым вводом ФИО, телефоны и два разных временных пароля, проверяет их, создаёт обоих руководителей одной транзакцией и не выводит секреты. Повторное создание запрещено. Передавать телефоны и пароли аргументами, в Git, чат, тестовые фикстуры или открытые логи нельзя. Общий короткий пароль не поддерживается. Временные пароли действуют 24 часа; первый вход требует замены. Безопасный порядок выдачи временного доступа владельцам нужно согласовать до реальной первичной настройки.

Два руководителя задаются отдельными фиксированными слотами и имеют одинаковые полномочия. Рядового сотрудника нельзя превратить в третьего руководителя через форму или подмену POST. Лидерам доступны создание и изменение сотрудников, назначение прав, блокировка и сброс паролей сотрудников. Удаление и замена двух основных руководителей не реализованы: для этого требуется отдельный согласованный процесс.

## Поведение

- Саморегистрации и публичного Django admin нет.
- Новому сотруднику генерируется независимый временный пароль; показывается руководителю на странице с `Cache-Control: no-store`, в базе хранится только Argon2-хеш.
- Первая смена пароля обязательна. Минимум 14 символов; нельзя распространённый, полностью цифровой или совпадающий с текущим пароль.
- У каждого сотрудника собственные разрешения; при создании все выключены.
- Изменение прав, телефона, статуса или пароля завершает старые сеансы. Смена своего пароля сохраняет только текущий сеанс.
- Два руководителя не могут молча затереть изменения настроек сотрудника: устаревшая форма отклоняется.
- Защита от перебора: окно 15 минут, 8 попыток на телефон и 40 на сетевой адрес. Учитываются все попытки; успешный вход сбрасывает счётчик телефона. В таблице ограничений используются хеши идентификаторов, не телефоны/IP в открытом виде.
- Документы подключены в версии 3.0.0. Общие права дополняются назначениями на объекты, доступом к договорам и отдельным открытием чужих документов. Полная политика: [DOCUMENTS.md](DOCUMENTS.md).
- Автоматическое восстановление по общей почте и аварийное восстановление обоих руководителей не реализованы: порядок ещё не согласован. Сотрудники восстанавливают доступ через руководителя.
- Журнал содержит существенные действия. Через веб-интерфейс он не изменяется; администратор БД технически может изменить базу. Внешняя защита журналов и резервирование относятся к размещению.
- Офлайн-вход и синхронизация не реализованы. Закрытое хранение документов и восстановление тестовых файлов/метаданных проверены; автоматическое резервирование NAS не настроено.

## Проверка

```sh
ARMADA_DEVELOPMENT=1 .venv/bin/python server/manage.py test accounts --verbosity 1
ARMADA_DEVELOPMENT=1 .venv/bin/python server/manage.py check
```

Браузерный тест использует Node, Playwright и Chromium (установлены в текущей среде), изолированную тестовую базу и одноразовые случайные пароли. Тестовые пользователи не остаются в рабочей базе. Для окружения без браузера серверные проверки: `test accounts.tests`; для полного прогона установить браузерные инструменты отдельно. Пароли в вывод тестов не записываются.

## До размещения в интернете

Нужны выбранный сервер, PostgreSQL, домен, HTTPS, резервные копии и правила восстановления доступа. Для production:

- `ARMADA_DEVELOPMENT` не устанавливать;
- передать `ARMADA_SECRET_KEY` (случайный секрет минимум 50 символов) из защищённого хранилища;
- задать `ARMADA_ALLOWED_HOSTS` и `DATABASE_URL` для PostgreSQL;
- HTTPS обязателен; сессии и CSRF-cookie получают Secure, сессия также HttpOnly и SameSite=Lax;
- `ARMADA_TRUST_PROXY=1` только если доверенный прокси удаляет входящий `X-Forwarded-Proto` клиента и выставляет собственный;
- при необходимости явно задать `ARMADA_CSRF_ORIGINS` с HTTPS-источниками;
- запустить миграции, `collectstatic`, `check --deploy`; обслуживать `/static/` каталогом `.runtime/static` через веб-сервер;
- запуск приложения: `.venv/bin/gunicorn --chdir server config.wsgi:application --bind 127.0.0.1:8020 --workers 2`;
- база, ключи и код не должны раздаваться веб-сервером; права пользователя БД ограничить нужными операциями, исключить публичный доступ к БД;
- проверить сохранение/восстановление БД, журналов и приватных файлов перед реальным наполнением.

Без production-секрета, списка хостов или PostgreSQL приложение отказывается запускаться. Значения секретов не включать в команды, переписку или файлы репозитория. Срок сеанса 8 часов, завершение при закрытии браузера; сохранение/восстановление вкладок самим браузером может влиять на фактическое закрытие. Эти начальные параметры можно скорректировать до эксплуатации.
