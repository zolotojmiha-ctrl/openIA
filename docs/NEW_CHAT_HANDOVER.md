| GitHub authentication | Предоставлялась платформой для Git; точный секрет не исследовался | Не путать с SSH и подписью |

XXXXXXXXXXXX — 12 символов отпечатка, не буквальное имя. Суффикс ключа восстановления нужно определить по существующему файлу; не выдумывать.

Ключ подписи и ключ восстановления — разные ключи. SSH-ключ не использовать для подписи выпуска. Пароль SSH не является ключом подписи.

Подтверждённый независимый отпечаток ключа подписи:
SHA-256 от DER SubjectPublicKeyInfo:

~~~text
e2f6b26419ccb10faa61baf1cfb5a0ea53f499da8803f23f0dd0df3f420aa3e4
~~~

Это не SHA-256 текстового PEM-файла.

Открытый ключ проверяется так:

~~~bash
openssl pkey -pubin -in ПУТЬ_К_ОТКРЫТОМУ_КЛЮЧУ -outform DER |
  shasum -a 256
~~~

У закрытого ключа выводят только публичную часть:

~~~bash
openssl pkey -in ПУТЬ_К_ЗАКРЫТОМУ_КЛЮЧУ -pubout -outform DER |
  shasum -a 256
~~~

На Linux вместо shasum можно использовать sha256sum. Если нужна фраза, владелец вводит её локально в терминале, не в чат.

15.11.2026 владелец уже получил «СОВПАДАЕТ: это прежний ключ подписи выпусков». Не просить повторять эту проверку в каждом сообщении.

Никогда:
- не проси cat закрытого ключа в вывод чата;
- не проси прислать пароль, токен или приватный PEM;
- не публикуй private keys в Git, ZIP, логи и Docker build context;
- не заменяй потерянный ключ новым автоматически;
- не считай тестовый signing.pem ключом компании;
- не меняй доверенный публичный ключ на VPS ради принятия новой подписи.

Если реальная копия ключа действительно потеряна, открытый ключ и старые подписи её не восстановят. Тогда нужен отдельный явный план смены доверия, а не обход проверки.

## 14. Резервные копии: точное объяснение владельцу

Нужно различать:
1. Установочный ZIP — код.
2. Резервный .encrypted — частные данные и настройки.
3. Recovery/checkpoint — прежнее дерево и закрытые настройки рядом с приложением.

Старый .encrypted может не отражать сегодняшнее наполнение базы. Для проверки расшифровки/механизма восстановления это допустимо, если ясно обозначены границы проверки. Эту старую базу не загружают вместо действующей при обычном обновлении.

Перед изменениями штатный установщик создаёт НОВУЮ копию текущих базы, документов и конфигурации после удержания писателей. Это актуальный предустановочный снимок.

Проверка старой копии:
- не является импортом старых данных;
- не заменяет свежую предустановочную копию;
- не означает проверку содержимого сегодняшнего production;
- не требует отправлять частный архив Codex.

15.11.2026 владелец успешно выполнил восстановление реальной копии локальным инструментом и вернул подписанный публичный результат. Codex проверил подлинность этого результата; частную базу не получал.

Для следующих обновлений не заставляй владельца без причины заново выполнять уже подтверждённую проверку неизменившегося механизма. Сначала используй зафиксированную квитанцию/результат и проверь, менялись ли формат, ключи или восстановитель. Если новая задача меняет backup/recovery или появились признаки проблемы, нужна соответствующая новая проверка.

Условие допуска: есть свежая предустановочная копия и хотя бы подтверждённый результат восстановления реальной копии. Нельзя ставить готовность по отсутствию ответа или ради продолжения установки.

Ретеншн без пригодной квитанции ничего автоматически не удаляет. Квитанция привязана к SHA-256 и имени копии. Старые квитанции и переименованные копии требуют внимания; не исправлять JSON задним числом ради удаления.

Новая предустановочная копия 6.33.1 шифруется публичным backup-recovery.public.pem из проверенного внешнего пакета; соответствующая закрытая часть остаётся у владельца. Это не переписывает настройки ключей Яндекс Диска/ЛК.

## 20. Что подписывается

Внутренняя подпись охватывает ровно:
- openIA-ВЕРСИЯ-update.zip;
- install-ВЕРСИЯ.sh;
- openIA-ВЕРСИЯ-update.json.

Создаются SHA256SUMS-ВЕРСИЯ и SHA256SUMS-ВЕРСИЯ.sig.

Внешний ZIP комплекта подписывается отдельно. В нём размещены внутренние файлы, подпись/ведомость и публичные ключи.

Открытый ключ из самого ZIP не является независимым источником доверия. До запуска установщика внешний ZIP проверяется ранее доверенным ключом с VPS; в облаке — по тому же заранее известному DER fingerprint.

Самопроверка исполняемого установщика не защищает его от модификации, которая убрала самопроверку. Поэтому внешняя проверка обязательна ДО запуска.

Подписание не заменяет испытания и восстановимость. ready_for_install=true не ставится ради прохождения установки.

Сейчас подписанный JSON 6.33.1 сохраняет некоторые поля момента сборки: status=candidate, published=false, production_installed=false. Одновременно ready_for_install=true и signature_created=true. Не «исправляй» подписанный JSON задним числом. Факт публикации/установки зафиксирован отдельно в docs/RELEASE_6_33_1_PUBLICATION.json и подтверждении владельца.

## 22. Публикация на GitHub

Установочные файлы — обычные Git-коммиты в downloads/nas-updates. Не требуется создавать GitHub Release или менять default branch.

Исходники публикуются отдельно от бинарных артефактов и частных данных.

Порядок:
1. Проверь готовность, подписи, суммы и ключ.
2. Получи актуальный HEAD downloads/nas-updates.
3. Сохрани прежние файлы. Добавь новые версионные пути без перезаписи.
4. Не добавляй частные планы, базы, .env, ключи восстановления/подписи, временные каталоги и сырые клиентские логи.
5. Сделай обычный commit и non-force push.
6. Зафиксируй полный SHA публикации.
7. Заново скачай ZIP, подпись и суммы именно по этому SHA.
8. Проверь независимый DER fingerprint, внешний SHA/подпись, состав ZIP, внутреннюю подпись и суммы, версию и исходный коммит.
9. Только теперь выдавай владельцу команду с неизменяемым URL.

Для публикации можно использовать отдельное временное дерево или безопасную сборку Git tree через временный index. Не удаляй/перемещай существующие checkout и пользовательские изменения. В этой среде применялся временный index, старые артефакты сохранены.

Если remote изменился параллельно, non-force push должен отказать. Проверь новые изменения и пересобери публикацию поверх актуального дерева; не делай force push.

Не подписывай результат тестовым ключом. Не переписывай существующую подписанную версию под тем же именем без отдельной договорённости. Для отдельного исправления используй новый уникальный пакет/версию и документируй накопительный состав.

## 26. Что делает штатный установщик

До остановки работающего приложения:
- проверяет каталог, версию, инструменты, доверенный ключ и подписи;
- проверяет наличие настроенного шифрования или явное решение об открытой копии;
- измеряет ресурсы и место;
- выявляет дополнительные локальные файлы;
- проверяет доступность безопасного recovery parent;
- собирает новый образ.

Затем:
- удерживает блокировки обновления, backup и disk worker;
- фиксирует ранее работавшие службы и точные image ID;
- останавливает писателей на резервирование;
- создаёт свежую согласованную копию;
- сохраняет старое дерево и .env;
- переключает дерево на том же filesystem;
- выполняет миграции и проверки;
- запускает и проверяет новую версию;
- возобновляет MAX только если он работал ранее.

Между резервированием и завершением нужных изменений запись не должна возобновляться. Не упрощай этот барьер ради «быстрого hotfix».

Параметры:
- --allow-local-files: только после анализа списка; файлы сохраняются в recovery/tree, но автоматически не применяются в новом дереве.
- --allow-unencrypted-backup: только явное решение владельца, не штатный обход отказа.
- --print-trust-fingerprint: чтение публичного отпечатка, не подпись и не установка.

Не добавляй разрешающие флаги во все команды заранее. Не трактуй безопасный отказ до остановки служб как повод выключить защиту.

- backup_done;
- switched;
- migrate_started;
- migrate_done;
- verify;
- complete.

До миграционного барьера установщик может вернуть прежнее дерево/точные image ID и ранее работавшие службы, проверив их.

После migrate_started:
- автоматического возврата схемы нет;
- писатели должны оставаться остановленными;
- если остановку Docker подтвердить не удалось, явно сообщить об этом;
- не запускать старый web поверх возможно изменённой схемы.

При migrate_done/verify допускается описанный в RECOVERY.md путь исправления новой версии:
- compose config --quiet;
- Django check;
- migrate --check;
- ожидаемая версия;
- контролируемая проверка здоровья и только потом решение оператора о писателях.

Не запускай compose config без --quiet в публикуемый вывод: там могут быть секреты.

При неподтверждённом завершении миграций основной путь — согласованное восстановление предустановочного комплекта БД, config и documents вместе с деревом/образами. Не заменять только один компонент наугад.

Никогда не использовать down -v, удаление database/documents volumes или удаление recovery как «обычное исправление». Не выполнять test fault injection на VPS.

От владельца запрашиваются только безопасные сведения: фаза, код, состояние служб, последние обезличенные строки. Не просить архивы .env/дампы/ключи. backup.log перед передачей нужно проверять на приватное содержимое.

## 28. Recovery после успеха

Recovery рядом с приложением содержит прежнее дерево и .env. Права 0700/root не делают его публичным.

После успешной 6.33.1 владелец получил путь вида:
 /opt/.armada-recovery-6.33.1.*

Его содержимое не загружать в облако, GitHub и чат. Автоматически не удалять.

Не удалять последний пригодный комплект и комплекты неудачных/незавершённых установок только по возрасту или количеству.

recovery_inventory.py — помощник чтения и классификации, а не разрешение на удаление. Флаг manual_cleanup_candidate сам по себе не доказывает наличие пригодного архива и полного пути восстановления.

Перед отдельной согласованной очисткой проверяется:
- завершение обновления и текущая работоспособность;
- доступность нужной предустановочной копии;
- наличие соответствующего ключа восстановления у владельца;
- пригодность последнего комплекта;
- отсутствие неразобранного сбоя.

## 29. Как общаться с владельцем

Владелец не обязан знать внутреннюю архитектуру, имена всех типов ключей и различие restore/signing. Объясняй конкретное действие простыми словами.

Хорошая инструкция:
- «В терминале Mac подключитесь этой командой».
- «Когда увидите root@…#, вставьте этот блок».
- «Выберите файл с таким назначением; ключи сюда не отправляйте».
- «Этот старый архив только проверяется изолированно; текущая база не заменяется».
- «Пакет опубликован по такому SHA, подписи проверены; вот точная команда».

Плохая инструкция:
- «Настройте всю новую инфраструктуру», хотя раньше работало без неё.
- «Вы же передавали ключ», когда речь могла идти о пароле.
- «Проверьте сами всё на Mac», хотя тесты должны идти в облаке.
- «Установите текущий неподписанный кандидат».
- «Подпишем потом», когда агент ещё не проверил доступность реального ключа.
- «Нужен токен GitHub», только потому что gh api не работает.
- «Обновление готово», когда пакет не подписан/не опубликован/не скачан повторно.
- «Я установил на VPS», когда установил владелец.

Не заставляй пользователя многократно подтверждать одно и то же. Сначала читай этот файл и текущие документы, проверяй доступные факты, затем спрашивай только конкретный внешний блокер.

Если владелец не понимает «резервная копия», объясни: это база, документы и настройки на случай восстановления. Не отвечай ещё одним техническим термином.

Если владелец прислал строку «ГОТОВО» и путь файла на Mac, это результат его инструмента, а не личная проверка файла агентом. Если он спрашивает, откуда известно наличие файла, объясни источник вывода и предложи открыть указанную папку. Не заявляй доступ к его диску и не проси весь каталог вместо одного публичного response.

## 30. Что делать, если потеряна ещё одна облачная среда

Из GitHub восстанавливаются:
- исходники по актуальному коммиту;
- публичные инструкции и инструменты;
- подписанные установочные файлы;
- проверочные описания и часть журналов, если они опубликованы.

Из GitHub не восстанавливаются автоматически:
- закрытые ключи;
- реальные базы/документы;
- частные JSON/таблицы;
- непубликованные логи и временные стенды;
- локальные файлы Mac;
- живые процессы.

Сначала проверь remote и доступность исходников, затем точно назови отсутствующее. Не заставляй заново проходить все шаги только из-за нового чата.

При потере только логов не объявляй утрату кода или работающего VPS. При отсутствии частного ключа не ищи его в публичных подписанных пакетах: там только открытая часть.

Это подсказки для поиска, не гарантированные пути новой среды. Авторитетные публичные источники — GitHub-коммиты и подписанные пакеты.
