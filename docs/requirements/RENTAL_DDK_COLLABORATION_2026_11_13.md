## Метод после ДДК

В обычной форме отметки ремонта и карточке мастера есть «После ДДК изменился метод ремонта». В меню выбранной работы MAX есть ссылка на ту же защищённую форму ЛК (выбор метода не переносится в отдельный бот-диалог). Мастер с правом отчёта по этой работе или внутренний сотрудник с repairs.prepare указывает новый метод, длину/состав/стенку при необходимости, дату ДДК и обязательное основание. Можно приложить до 20 файлов, до 10 МБ каждый / 40 МБ суммарно.

Исходные и новые параметры, автор, дата, основание и файлы сохраняются как запись plan_change с признаком ddk. Это не завершение ремонта: статус/дата фактического устранения/замер готового покрытия не создаются, материалы не списываются. Несовместимые резервы только этой работы снимаются действующим сервисом; подбор замен автоматический только при наличии stock.manage, без выдачи мастеру такого права. Потребность затем рассчитывается по новому требованию. Мастер отдельно вносит фактический результат и покрытие; далее обычная проверка руководителем.

Разрешён только действующий доступ/период ответственности; архивные/удалённые/закрытые работы и уже внесённый фактический монтаж блокируют изменение плана. Проверяются session_version, версия задания и уникальный токен. Повтор той же отправки не создаёт вторую историю/резервы/файлы, изменённый повтор отвергается. Чужие работы не открываются. Обновление не меняет назначенного мастера. После смены версии старый открытый черновик результата надо открыть заново.

## Наработка и MAX

Существующее напоминание мастеру в 20:00 Asia/Omsk сохранено. Руководителю отправляется новая отметка с датой, техникой, участком и 10/4/0 часами; при корректировке — прежние/новые часы и причина. Источник — атомарный аудит сохранения дня, не чтение страницы. Повтор сохранения того же состояния не создаёт уведомление. Перед доставкой проверяются текущая версия записи, актуальная привязка/роль и доступ.

В 21:00 Asia/Omsk руководитель получает одно предупреждение за текущий незаполненный день / ответственную аренду. Наличие MAX у мастера для предупреждения руководителя не обязательно. Заполненный день, включая явный ноль, подавляет предупреждение; позднее заполнение отменяет ещё не отправленное. Перезапуск/несколько обработчиков не создают второй логический запрос. Старые пропуски не рассылаются, после полуночи предупреждение истекает, часы никогда не проставляются автоматически. Догоняющий запуск после 21:00 возможен только за текущий день. Требуются включённый MAX-worker и действующая руководительская привязка; sent не означает прочтение.

## Внешний арендодатель

Добавлена роль lessor / «Арендодатель», пустой набор внутренних разрешений. Создаёт/редактирует руководитель. Новая учётка не создаёт карточку персонала и не получает корпоративную почту. Начальная профессия обычной новой формы остаётся прежней. Внутренние гранты этой роли не действуют даже при ошибочной записи в БД. Доступ к контрактам/объектам и внутренним URL не открывается: отдельный список разрешённых маршрутов, собственные страницы в существующем разделе «Техника», профиль/пароль/привязка MAX.

Руководитель в карточке аренды открывает «Доступ арендодателя», выбирает учётку и явную аренду. Это не весь парк техники или все аренды машины. По умолчанию только табель, часы, пропуски и собственные обращения; тарифы/начисления/оплаты этой аренды включаются отдельным флажком. Общий финансовый учёт, данные контракта, документы, другие аренды и редактирование часов закрыты. При неполных данных расчёт помечен неполным. Табель можно скачать, часы/разрешённые суммы — числовые ячейки; даты без отметки не считаются нулевыми.

Обращение о разногласии привязано к выбранной дате аренды, ограничено 2000 символами и уникальным токеном; сам табель не изменяет. Руководитель получает уведомление; руководитель/сотрудник с управлением арендой видит обращение в карточке и оставляет результат проверки. Решение становится видно владельцу и отправляется в его MAX при действующем доступе. MAX арендодателя показывает только его предоставленные аренды и ссылки на их табели; новые/исправленные отметки приходят только по предоставленной аренде, без сумм в тексте. Отзыв/деактивация/смена роли блокирует новые чтения, обращения и ожидающие сообщения; уже отправленные сообщения невозможно отозвать. Старые grants при отключении сохраняются для аудита, доступ явно закрывается; закрыть можно и для уже неактивной учётки.

## Потребность и названия MAX

Равные названия объекта/участка показываются один раз; отличающиеся сохраняются. Уведомление потребности агрегирует одинаковые типоразмеры по контракту/объекту/участку/диаметру/методу/длине/стенке; показывает DN и общее количество. Ограничение шести строк явно обозначает оставшиеся типоразмеры. Никакого перемещения/списания склада от уведомления.

Сравниваются фактические требования по работам/размерам/количеству/идентификаторам, без текстовых названий. Переименование само по себе больше не является сменой потребности. Для прежнего DemandWatch новая схема сравнения устанавливается один раз тихой базовой точкой, чтобы обновление формата не выдало ложное «изменилось»; текущая потребность всё время доступна в ЛК, далее реальные изменения снова уведомляются. Старые очереди с прежним digest отменяются проверкой актуальности. Для новой привязки исходная непустая потребность приходит как «Текущая нехватка».

## Ведомость ПТО на уровне контракта

Кнопка «Ведомость выполнения по контракту» находится на странице контракта «Выполнение работ», передаёт только contract без object/section и открывает все доступные участки этого контракта. Внутри остаются фильтры. Кнопка из ведомости отдельного участка убрана; общий вход из списка работ сохранён. Права и фактические результаты не расширяются/не меняются.

## Установка

Новые accounts.0031, projects.0036 и maxbot.0006: роль, новые таблицы доступа/обращений, версия сравнения потребности. Нет массовой выдачи прав/аренд, изменений старых часов/результатов/остатков. Перед миграциями остановлены прежние писатели, после проверок возобновляются web/mailworker и только ранее работавший MAX. Резерв БД/файлов и исходников, манифест исходных хэшей, подпись. Диагностика rental_collaboration_status только читает, на PostgreSQL READ ONLY; не ставит уведомления и не подтверждает реальные отправку/прочтение.
