# MAX: уведомлять о конкретном складском расходе

Владелец указал: после ДДК шлифовку заменили на П1, подходящее изделие было в свободном остатке. Сообщение «Потребность в муфтах изменилась» со списком всей нехватки вводит в заблуждение. Требование: вместо него показывать конкретную списанную муфту.

## Причина неоднозначности прежнего сообщения

`demand_watch.snapshot` сравнивает нехватку по работам, а текст объединял её по типоразмерам. Перераспределение свободного наличия между работами могло менять отпечаток при прежнем суммарном количестве. Первая инициализация также могла отправлять общий список. Это подтверждённые возможности кода, а не доказанная причина конкретного производственного сообщения: прежние строки снимка в DemandWatch не хранятся.

## Реализация

- Расчёт и просмотр потребности в существующем разделе «Склады» сохранены. Автоматическая рассылка общих изменений отключена. `queue_changes` отменяет только ожидающие сообщения `shortage:`; проверка доставки блокирует прежний `demand_digest`. Отправленная история сохраняется.
- `coupling_notices` получает событие сохранённого отчёта. Основание — реальные автоматические StockMovement `consume` и возвраты `reversal` списаний по этому отчёту. Резерв, просмотр подбора, фото, изменение плана и ручной реестр без складского движения не объявляются списанием.
- Сообщение на каждое конкретное движение: контракт, участок/работа, тип, DN, длина, стенка, заводской номер из снимка отчёта, код позиции, фактический склад из движения, количество и дата. UUID не подменяет заводской номер. При исправлении показан возврат прежнего изделия; новый расход — отдельным движением.
- Получатели: прежняя аудитория руководителей/ПТО с правом управления складом и доступом к работе. Перед доставкой повторно проверяются привязка, права, видимость работы и актуальность движения. Подтверждение отчёта руководителем не отменяет факта расхода.
- Отчёт, движения и очередь сохраняются одной транзакцией; повтор события не дублирует сообщение. Нет исторической массовой рассылки, новых меню, новых бизнес-действий или миграций. Складской учёт и алгоритм подбора не изменены. Обычное уведомление о проверке отчёта сохранено.

## Как выбирается изделие

При ДДК общий сервис смены плана может закрепить свободные точные плановые длины, если автор имеет `stock.manage`. Учитываются тип, диаметр, совместимая стенка, доступность склада, отсутствие чужого резерва/монтажа. Для П1 выбирается стенка с наибольшим покрытием, при равенстве — меньшая совместимая. Кандидаты точной длины сортируются по стенке, коду позиции и складу. Это не правило FIFO. Просмотр глобального подбора не создаёт резервов.

Сохранение результата использует конкретные выбранные/закреплённые Coupling, требует фактические номера в сценарии закреплённых изделий и создаёт расход со склада их реального остатка. Уже учтённое изделие повторно не списывается. Запись монтажа без связи со складским изделием сама по себе не создаёт складского расхода.

Для ответа о конкретной производственной муфте необходимы плановое изменение, снимок результата и реальные движения по работе. Доступа к производственной базе в этой проверке нет; номер изделия не устанавливается по скриншоту или по одному сообщению общей потребности.

## Проверки и границы

Синтетические проверки в облачном Linux: свободная П1 → ДДК → закрепление без расхода → отчёт → расход именно закреплённого изделия; повтор запроса/события; возврат при исправлении; отмена устаревшей доставки; отзыв роли; сохранение уведомления после подтверждения; откат транзакции; отсутствие ложного расхода для старого реестра; отмена старой очереди с сохранением sent-истории. Финальный прогон: 131 тест OK, 24,195 с; makemigrations --check --dry-run: No changes detected. Протокол — `docs/MAX_COUPLING_STOCK_NOTICES_VALIDATION.md`.

Внешний MAX и производственная база не проверены. Изменение исходников не означает установки на VPS. Ранее отправленные сообщения не редактируются и не удаляются.
