## Подтверждённые сведения API

Изучены официальные README.mdx и schema.yaml в https://github.com/max-messenger/api-schema на коммите 1a4a502fab096aa3a15d83d7ea95667ffb44d2ac (OpenAPI 0.0.33). SHA-256 схемы: 7e2fd072a67c6f830a02a55671eec88526f6a958b0c71ea4be96acecc3dd700b.

- Создание ботов доступно организациям, ИП и самозанятым — резидентам РФ. Нужны профиль https://business.max.ru/self, верификация, создание и модерация бота. Токен выдаётся после модерации. См. https://dev.max.ru/docs/maxbusiness/connection и https://dev.max.ru/docs/chatbots/bots-create/create . Токен в чат не запрашивать.
- API использует HTTPS к platform-api2.max.ru, Authorization в заголовке; секрет нельзя передавать произвольному адресу загрузки файла.
- Поддержаны bot_started, message_created, message_callback, изображения/файлы и кнопки. Привязка может использовать start payload. В описании deep link указан предел 128 символов, схема payload допускает 512: для совместимости укладываемся в 128.
- Подписки Webhook содержат секрет X-Max-Bot-Api-Secret. До вызова доменной логики необходимо проверить секрет, размер, типы полей и что это личный диалог. Ни имени, ни номера телефона недостаточно для идентификации.
- Спецификация прямо предупреждает, что Long Polling не подходит для production по скорости и сроку хранения событий. Для рабочего бота проектировать Webhook с надёжной входящей очередью, а не обещать бесконечную доставку /updates.

Сведения получены из официального репозитория, реальное подключение к API не выполнялось. Условия регистрации/модерации конкретной организации ещё не проверены.

## Сценарий

Привязка в существующем профиле ЛК: выдать короткоживущую одноразовую ссылку, принять идентификатор отправителя MAX, затем подтвердить привязку в авторизованном ЛК. Мастер видит свои работы, выбирает конкретный ремонт, вводит результат/препятствие и необходимые поля, прикладывает фото. Перед отправкой получает сводку и явно подтверждает. Платформа повторно проверяет пользователя, роль, доступ к работе и её версию. Сохранение выполняется через ReportForm и report_work, без отдельного обхода складских правил и проверки руководителя. Повтор того же подтверждения не создаёт второй отчёт.

Уведомления о возврате результата должны исходить из платформы после успешной записи решения, с отдельной очередью доставки. Потеря связи MAX не должна откатывать решение руководителя. Перед отправкой требуется повторная проверка действующей привязки и доступа; чувствительные подробности лучше открывать по ссылке в ЛК. Эта очередь пока не реализована.

## Исторический локальный прототип (первый этап)

server/projects/max_prototype.py — прототип диалога без сетевых запросов и внешней точки входа. Реализует выдачу/запрос/подтверждение и отзыв привязки, список доступных заданий, проверку черновика, явное подтверждение и идемпотентное сохранение через действующие сервисы. Фотография в тесте проходит штатный валидатор вложений, дополнительное декодирование PNG/JPEG в прототипе и закрытое хранилище. Штатное хранилище намеренно допускает непрозрачные вложения; это поведение не изменено. Неверное изображение отклоняется. Бот не подтверждает результат от имени руководителя.

В прототипе сессии хранятся в памяти одного процесса и исчезают при перезапуске. Это сознательно изолированная проверка сценария, НЕ production-хранилище. Модуль не подключён к URL, меню, обработчику MAX или рабочему сайту, не принимает непроверенные события. Новых миграций нет.

Смена версии сессии пользователя, деактивация, чужой диалог, переназначение задания, устаревшая версия и истечение черновика препятствуют отправке. Повторная привязка не оживляет прежние черновики.

## План после первого прототипа (исторический список)

1. Владелец регистрирует/верифицирует организацию, создаёт бота и проходит модерацию.
2. Реализовать постоянные модели привязок, входящих событий, файлов и подтверждений, очереди и ограничения частоты/объёма; проверить конкуренцию и восстановление после перезапуска. В памяти такие данные оставлять нельзя.
3. Добавить интерфейс привязки/отзыва в существующий профиль ЛК, защищённый Webhook с дедупликацией и транспорт MAX. Для фотографий отдельно проверить официальные адреса CDN, типы, размеры и потоковую загрузку; произвольный URL из сообщения скачивать нельзя.
4. Добавить очередь возвратов на доработку и повторы доставки с учётом неоднозначного ответа API. Не заявлять гарантию однократной доставки внешнего сообщения без поддержки API.
5. После доступности сервера проверить закрытый пилот с реальным ботом и тестовыми сотрудниками, затем отдельно включать рабочее использование.

ИИ не включён: сначала надёжный структурированный отчёт. В дальнейшем свободный текст/голос может готовить черновик, но не подменять числовые расчёты и авторизацию платформы. Автоматического включения массовых рассылок или публикации переписок нет.
