# Выпуск 6.33.1 через GitHub Actions

Рабочий VPS не используется для сборки или испытаний. Ручное подписание на Mac больше не требуется. Закрытый ключ не добавляется в Git, ZIP, чат или облачную среду разработки: единственная настройка — GitHub Environment secret для доверенного signing job.

## Однократная настройка владельцем

1. Settings → Environments → New environment: `armada-release`.
2. В этом Environment добавить secret `ARMADA_RELEASE_SIGNING_KEY`. Значение — полное содержимое существующего `armada-release-signing.key.pem`, включая строки BEGIN/END и переносы. Не отправлять ключ в чат и не создавать новый ключ вместо прежнего.
3. Ограничить deployment branches этого Environment веткой `main`. Workflow также проверяет repository/ref и запускается только вручную.
4. В Actions открыть **Release ARMADA 6.33.1** → Run workflow, ветка `main`.

Ссылка на настройки: https://github.com/zolotojmiha-ctrl/openIA/settings/environments
Ссылка на запуск: https://github.com/zolotojmiha-ctrl/openIA/actions/workflows/release-6.33.1.yml

Без отметки `restore_confirmed` workflow выполняет только проверку кандидата. Для подписи и публикации владелец должен подтвердить успешное восстановление реальной копии, указать её SHA-256 и время результата с часовым поясом (ISO 8601, например формат `ГГГГ-ММ-ДДTЧЧ:ММ:СС+06:00`). Не загружать саму копию, ключ восстановления, дамп или частную квитанцию в GitHub. Это заявление владельца, не автоматическая проверка восстановления; пустые, некорректные и будущие значения отвергаются.

Workflow проверяет именно эти байты и соответствие ZIP исходникам. Он собирает Docker-образ из проверенного кода, но не пересобирает ZIP с потенциально другими байтами. Для другого кандидата нужны новое независимое испытание и проверенное изменение фиксированных идентификаторов workflow/policy; произвольный ref в форму не принимается.

## Разделение задач

1. **validate** — без закрытого ключа: точные суммы, ZIP против исходников; сборка из закреплённых колёс; 60 тестов установщика в root-контейнере без сети; дополнительные наборы; настоящее синтетическое PostgreSQL-восстановление.
2. **sign** — защищённый `armada-release`, только после validate и подтверждения владельца. Используется доверенный helper из коммита workflow, а не код из кандидата. Ключ проверяется по фиксированному отпечатку, временный файл 0600 удаляется, в артефакты не входит. JSON получает подписанное подтверждение владельца и ready_for_install=true.
3. **publish** — отдельный runner без закрытого ключа. Снова проверяются подпись, независимый отпечаток и суммы. В `downloads/nas-updates` добавляются только пять версионных установочных файлов, без публичного проверочного ключа и без перезаписи существующих выпусков. Force push не используется.

Подпись не изменяет ZIP и установщик; JSON меняется, его сумма и подписанная ведомость формируются заново. Публичный ключ в промежуточном artifact не является источником доверия: его отпечаток закреплён в проверяющем коде, а на VPS используется уже доверенный отдельный ключ.

## После успешного Run

Summary задачи publish содержит ссылки на установщик, ZIP, подписанную ведомость и подпись по неизменяемому коммиту публикации. Затем владелец отдельно скачивает пять файлов на VPS, проверяет подпись ведомости существующим `/etc/armada/release-signing-public.pem`, проверяет суммы и запускает установщик с `ARMADA_APP_ROOT=/opt/armada` и настроенным `ARMADA_BACKUP_PUBLIC_KEY`. Закрытый ключ подписи на VPS не нужен. Параметры разрешения открытой копии и локальных файлов автоматически не добавляются.

Если версия уже присутствует в downloads, workflow отказывает вместо перезаписи. После частичного сбоя публикации требуется разбор результата; автоматически удалять или перезаписывать подписанный выпуск нельзя.
