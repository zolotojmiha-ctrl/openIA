# Яндекс Диск: первый этап резервирования

Статус: локальная реализация после 6.27.0. В опубликованный пакет 6.27.0 не входит. На рабочий VPS не установлена, реальный OAuth-токен не получен и живая загрузка не проверена. Фотографии и документы пока используют прежнее хранилище; переноса и удаления оригиналов нет.

## Подключение после восстановления VPS

Сначала проверить наличие и целостность прежней базы и файлов. Затем установить отдельно подготовленный и проверенный выпуск с этой реализацией и применить штатные миграции (добавляется projects.0031). Старый установщик 6.27.0 этой функции не содержит.

В ЛК руководителя открыть **Управление → Хранилище и резервные копии** по HTTPS:

1. Ввести OAuth-токен приложения с `cloud_api:disk.app_folder` и `cloud_api:disk.info`, сохранить. Токен зашифрован существующим ключом приложения, повторно не отображается. Пустое поле сохраняет прежний токен. Не отправлять его в чат, командную строку или Git.
2. Нажать «Проверить подключение». Проверяются квота и чтение папки приложения. Возможность записи проверяется при создании первой копии.
3. Скачать закрытый ключ восстановления, сохранить отдельно от VPS и подтвердить сохранение. На сервере остаются открытый ключ и его идентификатор. Повторно скачать тот же закрытый ключ нельзя. До подтверждения и создания заданий можно создать новый взамен несохранённого.
4. Администратор подключает обработчик на восстановленном VPS, из каталога приложения: `sudo bash deploy/beget/enable-disk-backups.sh`. При другом каталоге задать `ARMADA_APP_ROOT` перед вызовом. Скрипт по умолчанию использует существующий `/opt/armada/openIA-feature-accounts-foundation`; новый сервер/базу не создаёт.
5. Через несколько минут проверить сообщение об обработчике в ЛК. Нажать «Создать резервную копию сейчас» и дождаться статуса «Копия загружена и проверена».
6. Сначала провести пробное восстановление скачанной копии в изолированной среде. После этого включить ежедневное расписание в ЛК, если требуется.

Расписание изначально выключено, предлагаемое время — 03:00 по Омску. Обработчик опрашивает очередь каждые пять минут, начало может задерживаться до следующего опроса. Пропущенные дни не наверстываются. Включение после сегодняшнего времени запуска означает запуск завтра. За сутки создаётся не более одного автоматического задания, включая неудачные попытки; повтор возможен вручную. Уже выполняющаяся передача не является отменяемой операцией. Остановка автоматизации — снять флажок в ЛК; полная остановка обработчика — `sudo systemctl disable --now armada-disk-backup.timer` (текущая служба может ещё завершать работу).

## Что защищает копия

Обработчик запускает существующий `backup.sh`: приостанавливает записи web/mailworker, снимает PostgreSQL dump и файлы/конфигурацию, затем возобновляет сервисы. Это короткий период недоступности приложения. Веб-процесс только ставит задание в очередь; Docker socket ему не передаётся.

Архив шифруется потоково AES-256-GCM; случайный ключ архива защищается RSA-3072 OAEP SHA-256. Закрытый ключ восстановления не сохраняется в базе, конфигурации или на VPS. Результат помещается в `app:/armada/backups/` с уникальным UUID, без публичной ссылки и перезаписи прежних объектов. OAuth-заголовок уходит только фиксированному API; адреса передачи проверяются, передача идёт по HTTPS.

Успех фиксируется после полного повторного скачивания зашифрованного объекта и сверки SHA-256 и размера. Это проверяет передачу, а возможность расшифровки отдельно подтверждается пробным восстановлением с закрытым ключом. История содержит дату, размер, хеш и идентификатор ключа. Ошибка не выдаётся за успешную копию. Изменение настроек или отзыв прав автора блокируют ожидающие задания.

Локальные исходные архивы сохраняются в `/var/backups/armada`, режим каталога 0700. Они содержат конфиденциальные конфигурацию и файлы и доступны администратору VPS. Временный зашифрованный файл удаляется по завершении обработки. Автоматическая очистка локальных или облачных копий не реализована. На VPS нужно место для исходного архива и его зашифрованной копии одновременно; накопление исходных архивов пока требует контроля администратора. Эта стадия не освобождает место от фотографий. Диск не является неизменяемым хранилищем: доступ с правами записи не защищает от удаления копий владельцем токена.

## Восстановление без VPS и OAuth

Скачать `.encrypted` из папки приложения через Яндекс Диск. На отдельной машине с Python и установленной зависимостью `cryptography` запустить из каталога исходников:

```bash
PYTHONPATH=server python -m projects.disk_crypto \
  --source /private/backup.encrypted \
  --private-key /private/armada-recovery.pem \
  --output /private/restored-backup.tar.gz
```

Доступ к БД, настройки Django и OAuth для расшифровки не нужны. Путь результата должен быть новым. Файл публикуется только после проверки GCM; неверный ключ или повреждение не оставляют завершённый результат. Содержимое архива затем восстанавливается штатной процедурой в **отдельную пустую базу и отдельные тома**, с проверкой внутренних SHA256SUMS. Не распаковывать поверх работающего сервера. Сохранять совместимые исходники/пакет и закрытый ключ отдельно от Beget.

## Границы проверки

Автоматические тесты используют синтетический токен и подмену API, без обращения к аккаунту владельца. Реальные разрешения аккаунта, доступность сервиса, подписанные адреса передачи и ограничения тарифа нужно проверить при первом подключении после восстановления VPS. Повторное скачивание удваивает передачу данных для каждой копии. Политика хранения, перенос фотографий, превью/кеш и обслуживание больших объёмов — следующие отдельные этапы.

## Локальная защита и политика хранения с 6.31.0

`backup.sh` сохраняет согласованный дамп, число строк по таблицам, конфигурацию/документы и манифест их содержимого. Каталог 0700. Для локального шифрования явно задать `ARMADA_BACKUP_PUBLIC_KEY=/etc/armada/recovery-public.pem`; это **открытый** ключ того же формата, что выдаётся в ЛК. Закрытый ключ на VPS не переносить. Для standalone CLI нужен Python с cryptography (`ARMADA_BACKUP_PYTHON` задаёт путь к подготовленному Python). Неподходящая среда обнаруживается до остановки служб. Без параметра остаётся прежний незашифрованный локальный архив, доступный root.

Дисковый обработчик принимает зашифрованную локальную копию без повторного шифрования, только если идентификатор её открытого ключа совпал с ключом задания ЛК; иной ключ — явная ошибка, локальный файл сохраняется. Никаких новых внешних отправок по умолчанию нет.

Политика `ARMADA_BACKUP_KEEP` (по умолчанию 7) и `ARMADA_BACKUP_DAYS` (30) сохраняет минимум указанное число копий и минимум указанный срок. Дополнительно сохраняются последняя подтверждённо восстановленная копия и все копии новее неё. Пока нет действительного подтверждения восстановления, автоматическое удаление **вообще не выполняется**. Подтверждение — файл `<архив>.verified.json` с совпадающим SHA-256, полученный на доверенном стенде. Права каталога и ограничение root не защищают от злоумышленника с root; внешнюю копию хранить отдельно. Неизвестные файлы/симлинки и checkpoint обновлений политика не удаляет. Политику можно проверить без удаления:

```bash
python3 deploy/beget/backup_retention.py --directory /var/backups/armada --keep 7 --days 30
```

### Периодическая проверка на доверенном компьютере

Загрузить/скопировать закрытый архив отдельно от VPS. На доверенном Linux/Docker-стенде с Python/cryptography и заранее загруженным PostgreSQL 17 (не на рабочем сервере) запустить:

```bash
python3 deploy/beget/verify_latest_backup.py \
  --source-directory /private/armada-copies \
  --receipt-directory /private/armada-receipts \
  --private-key /private/armada-recovery.pem
```

Эту команду можно запускать ежедневно планировщиком **этого доверенного стенда**. Она проверяет последний архив, при необходимости расшифровывает его, сверяет хэши, действительно распаковывает файлы, восстанавливает дамп в отдельный временный PostgreSQL без сети/рабочих томов и сравнивает число строк. Данные и ключи в вывод не попадают; временная БД/файлы удаляются. Закрытый ключ остаётся здесь. Службу на VPS автоматически не устанавливать. Подтверждение можно отдельно перенести администратором в каталог локальных копий, только для архива с тем же SHA-256; это разрешает последующую очистку старых копий. Настройка доставки архива на доверенный стенд и расписания требует реально выбранного хоста, здесь не включалась.

Для старых архивов без числа строк/манифеста автоматическое подтверждение не выдаётся — требуется прежнее ручное восстановление. Оно не подменяется одной проверкой хэша/списка дампа. Ошибка проверки не выдаётся за успешное восстановление.

## Исправление серверного обработчика — 11 ноября 2026

На новом VPS владелец подтвердил доступ к Яндекс Диску через ЛК и сохранение recovery-ключа. Первая передача завершилась до запуска команды Django: root-процесс upload при унаследованном cap_drop ALL не мог читать UID10001/0600 django-key. Исправлен только хостовый disk-backups.sh: одноразовому root-загрузчику добавлен DAC_OVERRIDE, как уже сделано для tar резервирования. Права файлов конфигурации и работающего web не меняются, privileged и Docker socket внутри приложения не добавлены. Сборка образа/миграции не требуются. Три теста HostWorkerTests прошли, включая требование ровно этого дополнительного capability для upload и его отсутствие в exec. Реальную загрузку на Диск нужно повторить после установки исправления, не объявлять её успешной по тестам. Подписанный архив 6.31.0 остаётся прежним; исправление распространяется отдельно до следующего выпуска.

Дополнительно на настоящем armada-web:6.31.0 без сети воспроизведено чтение синтетического файла UID10001/0600: root с cap_drop ALL получает PermissionError, после добавления только DAC_OVERRIDE читает файл; владелец/режим внутри контейнера прежние. Лог /workspace/armada-release-6.31.0/hotfix-disk/permission.log. Рабочие ключи и API не использовались.

### Адрес обратного скачивания Яндекс Диска

После установки исправления DAC_OVERRIDE владелец проверил реальный API: чтение/создание папок/получение upload URL — OK. Отдельный маленький синтетический файл зашифрован и загружен, затем удалён. При обратном скачивании проверка адреса отказала; безопасная диагностика без вывода URL/токена подтвердила HTTPS-перенаправление downloader.disk.yandex.ru → mds.storage.yandex.net. Добавлен только точный mds.storage.yandex.net, без wildcard storage.yandex.net, HTTP/userinfo/иных портов. 29 тестов projects.test_disk_backups прошли на изолированной SQLite, включая цепочку redirect/readback SHA-256, отказ при подмене содержимого, отсутствие OAuth в CDN-запросах и блокировку похожих/посторонних адресов. Реальную повторную полную копию ещё нужно проверить на VPS после пересборки образа. Подписанный ZIP 6.31.0 не переписывается; это отдельное исправление Python-клиента в образе.

### Первая реальная проверенная загрузка — 11 ноября 2026

Владелец установил серверный исправленный disk-backups.sh (24f931c), заменил Python-клиент на ce930b0, пересобрал web и прислал healthy. После повторного задания показал в ЛК «Копия загружена и проверена», размер 102,4 КБ, SHA-256 отображён. Это подтверждает реальную загрузку зашифрованной копии на Диск и полный readback/hash после двух исправлений, по предоставленному владельцем скриншоту; прямого доступа разработчика к VPS/токену не было. Два прежних failed-задания остаются историей ошибок. Расшифровка/фактическое восстановление именно этой рабочей копии ещё не проверены; не подменять их статусом verified (он означает readback). Ежедневное расписание оставлено выключенным; timer был остановлен при диагностике и его запуск заново ещё не подтверждён. Ручной systemctl start службы сработал.
