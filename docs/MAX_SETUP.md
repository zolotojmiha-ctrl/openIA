## Что делает бот

1. Мастер открывает **Мой профиль → Подключение MAX**, создаёт одноразовую ссылку (10 минут), запускает бота и подтверждает запрос обратно в авторизованном ЛК. Знание имени или телефона не даёт доступа. Роль, активность, обязательная смена пароля и версия сеанса проверяются заново.
2. В личном диалоге кнопка «Мои работы» показывает только доступные назначенные работы, с выбором участка и страницами. Одна работа может объединять несколько дефектов.
3. Мастер выбирает «Работа выполнена» либо «Не выполнена / препятствие». Вопросы формируются из действующей `ReportForm`, включая дату, координаты, фактическую длину, состав, заводские номера, пояснение и фактическое снятие изоляции там, где это уже предусмотрено формой. Подготовленные складом муфты определяют поля так же, как в ЛК. Неприменимые поля не показываются.
4. Затем можно добавить PNG/JPEG, до 20 файлов, 10 МБ каждый и 40 МБ суммарно. Предельное изображение — 16 млн пикселей и 8000 по стороне. Источники фотографий разрешаются только после проверки точных HTTPS-хостов CDN на пилоте; по умолчанию список пуст и фото через MAX отклоняются с предложением использовать ЛК. Произвольные ссылки из текста не скачиваются, редиректы запрещены, токен не передаётся CDN.
5. Бот показывает сводку, позволяет исправить поля и принимает только явное подтверждение. Полная форма проверяется снова, а сохранение выполняет штатный `report_work`: расчёты, монтаж/склад, история и проверка руководителя не обходятся. Метод ремонта из задания не меняется ботом с расширением прав мастера; нестандартные изменения выполняются через предусмотренные действия ЛК.
6. Возврат руководителем создаёт уведомление со ссылкой на карточку в той же транзакции, что и решение. Сетевая отправка выполняется отдельно. Перед отправкой повторно проверяются доступы; отменённые или уже устранённые замечания не отправляются.

Черновики хранятся 2 часа, их состояние и вложения переживают перезапуск процесса. `/работы` открывает список, `/отмена` отменяет черновик, `/удалить_фото` удаляет фото на этапе вложений. Отзыв привязки отменяет незавершённые черновики; повторная привязка их не оживляет. Повтор одного события/подтверждения не создаёт второй отчёт.

## Серверная конфигурация

Секреты вводить только на сервере, не в чат, Git, аргументы команд или `.env`. Поддержаны `ARMADA_MAX_TOKEN_FILE` и `ARMADA_MAX_WEBHOOK_SECRET_FILE`. Сам токен должен храниться в закрытом файле, доступном UID приложения; webhook secret — отдельная случайная строка длиной 32–256 из `A-Z a-z 0-9 _ -`. Они должны попадать в защищённую копию конфигурации. Доступ разработчику к реальным секретам не требуется.

Несекретные настройки `deploy/beget/.env` после подготовки файлов:

```dotenv
ARMADA_MAX_ENABLED=1
ARMADA_MAX_TOKEN_FILE=/run/armada/max-token
ARMADA_MAX_WEBHOOK_SECRET_FILE=/run/armada/max-webhook-secret
ARMADA_MAX_BOT_NAME=ИМЯ_ИЗ_ССЫЛКИ_MAX_БЕЗ_СОБАКИ
ARMADA_MAX_PUBLIC_ORIGIN=https://app.armada-sibir.ru
# Только подтверждённые точные хосты фотографий. Не добавлять wildcard/весь интернет.
ARMADA_MAX_PHOTO_HOSTS=
```

Это пример, а не готовая конфигурация: имя бота необходимо сверить с его публичной ссылкой. Для формирования подписки `setup_max_webhook --apply` проверяет имя бота через `/me` и отказывается менять подписку при несовпадении. Реальный API и формат имени ещё требуется проверить на пилоте.

После установки проверенного нового выпуска и наличия HTTPS на 443:

```bash
docker compose -f deploy/beget/compose.yml up -d web mailworker
docker compose -f deploy/beget/compose.yml exec -T web python server/manage.py setup_max_webhook
# Следующая команда регистрирует реальную подписку; выполнять при готовности к пилоту.
docker compose -f deploy/beget/compose.yml exec -T web python server/manage.py setup_max_webhook --apply
docker compose -f deploy/beget/compose.yml --profile max up -d maxworker
```

Webhook: `/integrations/max/webhook/`, секрет в `X-Max-Bot-Api-Secret`, тело до 64 КиБ. Принимаются только поддерживаемые события личного диалога. Ответ 200 означает, что событие сохранено в базе, а не что отчёт уже записан. Ошибка записи в БД не подтверждается успешным ответом. Дедупликация использует идентификаторы сообщений/нажатий и хэш запроса запуска, необработанный одноразовый код в очереди не сохраняется.

Проверка без отправки сообщений:

```bash
docker compose -f deploy/beget/compose.yml exec -T web python server/manage.py process_max
docker compose -f deploy/beget/compose.yml exec -T web python server/manage.py maintain_max
```

`process_max` без `--deliver` обрабатывает входящие события, но не делает сетевые отправки. Постоянный MAX-worker запускается с `--loop --deliver`. Он не использует Docker socket. Исходящие запросы идут только к зафиксированному origin официальной схемы `https://platform-api2.max.ru`; TLS-проверка включена, секреты не передаются в URL.

## Очереди, сбои и резервирование

- Inbox и Outbox — в PostgreSQL, вместе с привязками и черновиками. В одной транзакции сохраняются отчёт, состояние черновика, обработка события и ответ. Обработка сотрудника сериализуется блокировкой его строки. Исходящие сообщения одного диалога сохраняют порядок; запоздалые текстовые ответы отклоняются по времени события MAX; устаревшие меню проверяют доступ к перечисленным работам/участкам.
- Перед сетевой отправкой фиксируется `sending`. HTTP Retry-After учитывается при откладывании повторов. После успешного ответа — `sent`. HTTP 429 откладывает повтор (максимум 5 попыток). При таймауте/5xx или перезапуске после `sending` — `unknown`, без автоматической повторной отправки: MAX может уже принять сообщение. Ошибки 4xx, кроме 429, — `failed`. Это не обещание строго однократной внешней доставки. Отчёты при этом не дублируются.
- Внешний запрос, уже ушедший в MAX одновременно с отзывом доступа, невозможно отозвать. Привязка и доступ проверяются перед отправкой; содержимое уведомлений ограничено, переход в ЛК требует авторизации.
- `maintain_max --cleanup` ежедневно удаляет истёкшие запросы привязки, старые счётчики, содержимое просроченных черновиков и их отдельные копии фото; спустя 7 дней очищает payload событий и тексты завершённых/истёкших исходящих. Отчёты и штатные вложения не удаляются. Хэши обработанных событий сохраняются для защиты от повторов. Команда выводит только количества по состояниям. Файлы удаляются после фиксации транзакции. Авария процесса непосредственно между записью файла и фиксацией метаданных может оставить сиротский закрытый файл, как и в штатном хранилище; автоматического удаления неизвестных файлов нет.
- `backup.sh` останавливает все реально работающие писатели (`web`, `mailworker`, опциональный `maxworker`) и возобновляет только их. Нельзя запускать отдельный MAX-worker вне этого перечня во время резервирования. Ежедневную очистку тоже не запускать одновременно с резервированием. Восстановление делается с выключенным MAX; после него проверить состояние `sending/unknown`, доступы и подписку, затем отдельно включить worker.
- Обновление/восстановление будущего выпуска также обязано остановить MAX-worker перед миграциями/заменой файлов. Проверка нового установочного ZIP и восстановления с MAX требуется перед объявлением нового выпуска готовым. Существующий установщик 6.29.0 для установки MAX не использовать.

## Закрытый пилот перед рабочим включением

Нужны доступный HTTPS-сервер и безопасно настроенный токен. На синтетическом сотруднике проверить `/me`, подписку/секрет, структуру событий MAX, подтверждение привязки, чужой участок, обе формы результата, PNG/JPEG с проверкой реального CDN, повтор события, возврат руководителем и отзыв доступа. Отдельно проверить перезапуск очереди, остановку worker на резервирование и восстановление копии с отключёнными отправками. ИИ и голосовое распознавание в эту интеграцию не входят.

Для отключения сначала остановить `maxworker`, затем выставить `ARMADA_MAX_ENABLED=0` и пересоздать web/mailworker с обновлённой средой. Одного изменения `.env` недостаточно: уже работающий процесс продолжает использовать прежние переменные. Отзыв конкретного мастера выполняется через его профиль без перезапуска сервисов.

## API TLS и первый реальный /me — 11 ноября 2026

На VPS созданы max-token и max-webhook-secret, содержимое не передавалось разработчику. Публичный никнейм бота id8606018748_bot подтверждён владельцем по результату GET /me: is_bot=True. Временный запрос прошёл после добавления CA только в SSLContext данного запроса. platform-api2.max.ru обслуживается сертификатом *.max.ru от Russian Trusted Sub CA; обычные корни Ubuntu/контейнера не доверяли цепочке. Официальный README api-schema на актуальном коммите 0016ff3b8cd54c3842b662c8a440eb87ed9cb2b1 прямо требует platform-api2.max.ru и доверия сертификату Минцифры; переход на старый platform-api.max.ru не используется.

Публичный корень скачан владельцем по HTTPS https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer. SHA-256 DER: d26d2d0231b7c39f92cc738512ba54103519e4405d68b5bd703e9788ca8ecf31; срок до 27 февраля 2032. Перед размещением в config нужно сверить fingerprint. Постоянный путь в томе конфигурации: /run/armada/max-api-ca.pem, root-owned/0444. Это публичный сертификат, не ключ.

Исправленный клиент maxbot.transport добавляет этот файл (при его наличии) к стандартным корням через отдельный SSLContext только для фиксированного MAX API. Проверка имени/цепочки обязательна, NoRedirect остаётся. Глобальное доверие сервера, браузера, почты и CDN фотографий не меняется. Неверный файл CA завершает запрос отказом. Веб и MAX-worker используют одинаковый образ/конфигурацию; после замены transport.py нужна пересборка и пересоздание служб.

Проверки: 53 теста maxbot на изолированной SQLite — OK, 2 PostgreSQL-конкурентных сценария пропущены; 4 новых реальных loopback TLS-сценария прошли также в штатном read-only/UID10001/cap_drop ALL контейнере без сети. Проверены доверие тестовому CA только у API, сохранение CERT_REQUIRED/check_hostname, отказ без CA/с повреждённым CA до передачи токена, запрет follow redirect. Реальных запросов к MAX из облака/рабочих секретов не было. Подписанный выпуск 6.31.0 не переписывается; это отдельное исправление перед пилотом.
