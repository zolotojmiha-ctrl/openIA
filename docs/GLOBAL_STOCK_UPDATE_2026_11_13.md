# Следующий этап: совместное распределение наличия

Предыдущий исправляющий пакет П1 установлен владельцем (сообщение о Healthy и сохранённых резервах). Этот пакет добавляет новый механизм, не переписывает старый архив.

Складские сочетания рассматриваются совместно для всех незавершённых работ. Цель — максимум различных дефектов, закрываемых наличием. Закреплённые/смонтированные муфты остаются на своих работах. Закупка рассчитывается только после подбора; для свободной потребности 3000 мм основной вариант 1500+1500, а реальный складской комплект может быть 1000+2000. Заказчику передаётся один вариант остатка.

В «Склады → Потребность в муфтах» раскрывается «Подбор из наличия». Предварительный расчёт не записывает резервы. Отдельная кнопка утверждает показанные полные комплекты (до 20 за раз), перепроверяя остатки и права в одной транзакции. При изменении исходных данных требуется пересчёт. Повторное утверждение того же предложения не создаёт дублей.

Миграций нет. Письма и MAX используют тот же расчёт. Старую неподанную потребность необходимо сформировать заново: снимки прежних алгоритмов не отправляются. Реальные письма/уведомления при разработке не отправлялись, сервер напрямую не изменялся.

Проверки:

- 353 проверки SQLite/Chromium — OK, 87,483 с; два PostgreSQL-сценария пропущены в этом прогоне. Существующие отчёты, составная П1, потребность, письма/Excel, фактическое покрытие, MAX и складские браузерные сценарии.
- 31 профильная проверка PostgreSQL 17 — OK, 7,070 с. Дополнительно 14 PostgreSQL/Chromium — OK, 7,844 с, включая конкурентное утверждение одного предложения двумя соединениями.
- После добавления выделения из старой групповой позиции: 19 SQLite/Chromium — OK, 5,557 с, один PostgreSQL-тест пропущен. Включены независимая сверка 12 наборов с полным перебором физических назначений, максимизация именно дефектов, альтернативы 1000+2000 и 1500+1500, сохранение прежних резервов/стенки, откат всей транзакции, подпись/права, устаревшие версии, отсутствие записей при просмотре, повторное утверждение.
- Офлайн Docker-сборка с обязательными хэшами всех wheel прошла. В образе выполнены 11 профильных тестов — OK, 1,759 с, один PostgreSQL-тест пропущен. Нативные highspy и NumPy загружены и реально выполняли подбор.
- Интерфейс Chromium: раскрытие, явное закрепление, отсутствие повторной кнопки после сохранения; ширины 320/390/768/1440. Таблица на телефоне прокручивается внутри панели, не расширяет страницу.

Масштабирование: синтетические 20/100 работ с общими складами — доказанный оптимум за 1,676/1,892 с; трудный набор 300 работ достиг лимита 15 с и корректно отклонён. Это измерения конкретных синтетических наборов, не гарантия времени любой базы. Независимые группы разделяются точно, одинаковые физические остатки объединяются, равнозначные перестановки работ исключаются. Все ограничения и порядок приоритетов — в [требованиях](requirements/GLOBAL_COUPLING_ALLOCATION_2026_11_13.md). При недоказанном расчёте заказ не формируется; приближённая потребность не подменяет точную.

Установка: отдельный подписанный `armada-global-stock-update.zip`. Установщик проверяет исходные файлы и комплект, сохраняет резервную копию данных/исходников, собирает образ до замены контейнеров, проверяет новые библиотеки, перезапускает web/mailworker и ранее работающий MAX-worker. Никакие резервы при установке не создаются. Восстановление исходников из напечатанного каталога `global-stock-source-*` с последующей сборкой; данные без необходимости не восстанавливать поверх более новых изменений.
