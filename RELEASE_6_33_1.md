## 2. Что изменено

### Оценка свободного места (пункт 2)
Старые 2 ГБ заменены оценкой пикового дополнительного расхода по файловым системам (до остановки писателей и изменения дерева). Это верхняя оценка, а не гарантия.

| Расход | Формула (байт) | Где |
|---|---|---|
| Пакет | размер zip + сумма размеров файлов в нём | каталог временных файлов |
| Резервная копия | D = размер БД (`pg_database_size`) + размер `/run/armada` и `/var/lib/armada-documents` (`du`); без ключа 2D, с ключом 3D (каталог dump/config/documents, `.partial` и `.encrypted` существуют одновременно; сжатие не засчитывается) | каталог копий |
| Новое дерево | сумма размеров файлов пакета (`copytree` в recovery); переименование старого дерева на одном томе не считается копированием | каталог рядом с приложением |
| Образ Docker | размер текущего образа + сумма размеров файлов пакета (верхняя граница новых слоёв) | `DockerRootDir` |

Расходы одной файловой системы суммируются; к сумме добавляется запас 25% и 512 МиБ на файловую систему. Файловая система определяется по `df -Pk` (устройство и точка монтирования). Ошибка измерения (нет числа, нет `DockerRootDir`, разные ФС приложения и recovery) - отказ. При отказе выводятся том, необходимое и доступное место и роли расходов, без путей к данным.
Служебные действия предпроверки (перечень полный): чтение архива; `df`; `docker info`; `docker image inspect`; `compose ps/config`; один запрос `SELECT pg_database_size(...)`; одноразовый контейнер только для `du` (`run --rm`). Службы не останавливаются, дерево не меняется.

### Recovery (пункт 3) и фазы (пункт 4)
- Перед созданием проверяется родительский каталог (root, не симлинк, нет записи для посторонних без sticky), после - сам recovery (root, 0700, не симлинк). Отказ до остановки служб.
- Файл `phase` записывается атомарно с fsync; переменная состояния меняется только после успешной записи. Журнал `phases.log` (время по Омску). Фазы: `prepare`, `backup_done`, `switched`, `migrate_started`, `migrate_done`, `verify`, `complete`. Нет записи `migrate_done` - значит миграции не подтверждены.
- При ошибке после барьера: писатели останавливаются и не запускаются автоматически, пишется `failure.txt` (фаза, код, без команд и настроек) и в `RECOVERY.md` добавляется состояние. Путь А (диагностика и исправление новой версии: `config --quiet`, Django `check`, `migrate --check`, проверка версии, контролируемый запуск и healthcheck) допустим только при `migrate_done`/`verify`; при `migrate_started` основной путь - Б (согласованное восстановление БД, config, documents, дерева и образов).
- Автоматического удаления recovery нет; `.env` не шифруется. После успеха и при сбое печатается путь и предупреждение о закрытых настройках.
- Только чтение: `python3 deploy/beget/recovery_inventory.py --directory <каталог рядом с приложением>` классифицирует комплекты (complete, failed, incomplete, unknown) и помечает кандидатами на РУЧНУЮ очистку только завершённые комплекты старше последнего завершённого.

Ручная очистка (порядок): 1) выполнить инвентаризацию; 2) не удалять последний завершённый комплект и любые комплекты неудачных, незавершённых или неизвестных обновлений; 3) убедиться, что предустановочная копия из `archive` проверена восстановлением (квитанция) и не нужна; 4) удалять только вручную, каталог содержит `.env`.

### Локальные файлы (пункт 5)
До остановки служб существующее дерево сравнивается с составом пакета. Исключения (точные): `.env`, `.env.*` только в корне и в `deploy/beget` (если это ссылка или каталог - жёсткий отказ), `.armada-update.lock` в корне, каталог `.git`. Остальное, чего нет в пакете, показывается относительными путями (содержимое не читается) и установка завершается отказом. `--allow-local-files` разрешает продолжить: файлы остаются в `recovery/tree`, список в `recovery/local-files.txt`; в новую версию они автоматически НЕ применяются (override-файл не заработает без ручного действия).

Мой вывод/решение, не из задания: «состав пакета» недостаточен как эталон, потому что файлы прошлых выпусков, удалённые в новом, выглядели бы как локальные. Поэтому пакет содержит `deploy/beget/release-files.txt` (точный состав выпуска, для следующего обновления) и `deploy/beget/known-release-paths.txt` (пути прошлых выпусков, которых в новом нет). Для кандидата 6.33.1 второй список построен из коммитов c3429b05 и 6ea8a63 по правилам упаковки; это реконструкция, а не снимок реального дерева на VPS. Файлы, добавленные позже накопительными «fix»-пакетами и отсутствующие в этих коммитах, будут показаны как лишние: безопасный отказ, продолжение через `--allow-local-files`.

### Копии по умолчанию (пункт 6)
- Без `ARMADA_BACKUP_PUBLIC_KEY` `backup.sh` печатает заметное предупреждение; установщик требует `--allow-unencrypted-backup` (иначе отказ до остановки служб).
- При заданном ключе: нет файла ключа или модуля `cryptography` у выбранного Python (`ARMADA_BACKUP_PYTHON`, путь указывается в сообщении) - отказ; ошибка шифрования - открытая копия удаляется, перехода на незашифрованный режим нет. Проверка выполняется в предпроверке установщика (`backup.sh --preflight`), до остановки служб.
- После копии пишется `backup-status.json` (0600): шифрование, число копий, число копий с квитанцией, копий без подтверждения после последней подтверждённой, порог (по умолчанию равен `ARMADA_BACKUP_KEEP`, 7), предупреждения `unencrypted_backup`, `too_many_unverified_copies`. Удалений он не делает.
- Квитанция `<копия>.verified.json` связана с копией: `restored`, имя копии (`archive`) и SHA-256 текущих байтов копии. Квитанции старого формата без имени не принимаются (безопасно: удаления нет). Скачанная копия, переименованная браузером, даст квитанцию с другим именем: перед сохранением проверьте имя.

### Закрытие hotfixes (пункт 7)
Все 22 `deploy/hotfixes/install-*.sh` заменены заглушками: печатают отказ и завершаются кодом 3 без единой команды (нет бэкапа, Docker, сети, остановки служб, изменения файлов). Исторические тексты сохранены в `deploy/hotfixes/historical/*.disabled` (не исполняемые, в установочный пакет не входят). Уже скачанные владельцем старые скрипты отозвать нельзя. Эталон нового дерева - состав конкретного проверенного подписанного выпуска; частные `.env*` и файлы, явно разрешённые `--allow-local-files`, учитываются отдельно.

### Подпись (пункт 9)
`bash install-6.33.1.sh --print-trust-fingerprint` печатает SHA-256 от DER-кодировки SubjectPublicKeyInfo доверенного ключа (64 символа, нижний регистр) и ничего не меняет. Независимо от установщика: `openssl pkey -pubin -in /etc/armada/release-signing-public.pem -outform DER | sha256sum`. Это то же значение, что `sign_release.py` записывает как `signing_public_key_sha256`. Сравнивайте с отпечатком, полученным от владельца выпуска по независимому каналу.

## 3. Памятка владельцу

Предварительные условия: восстановление РЕАЛЬНОЙ копии на доверенном Mac подтверждено (иначе кандидат не готов к боевой установке); есть доверенный открытый ключ в `/etc/armada/release-signing-public.pem` (root, без записи для посторонних); задан `ARMADA_BACKUP_PUBLIC_KEY` или вы осознанно используете `--allow-unencrypted-backup`; в каталоге копий и рядом с приложением достаточно места (установщик проверит).

1. Проверка до запуска (на Mac или любой доверенной машине, не на VPS): `openssl dgst -sha256 -verify <открытый ключ> -signature SHA256SUMS-6.33.1.sig SHA256SUMS-6.33.1`, затем `sha256sum -c SHA256SUMS-6.33.1` для zip, установщика и JSON. Сравните отпечаток ключа (см. выше). Установщик не должен запускаться, пока любая проверка не пройдена.
2. Подписание (только вы или доверенный механизм): `ready_for_install` в JSON меняется на `true` только после подтверждённого восстановления реальной копии; `sign_release.py` пересчитывает JSON (`signature_created`, отпечаток), поэтому после подписания нужно заново проверить SHA-256 JSON и вновь сформированную ведомость. Подпись не заменяет доказательство испытаний.
3. Установка на VPS (под root): отдельная команда подключения с Mac и отдельная команда установки, например `bash install-6.33.1.sh [--allow-unencrypted-backup] [--allow-local-files]`. Точные команды подготовим после подписи.
4. После установки: установщик сам проверяет `check`, `migrate --check`, версию и healthcheck; затем проверьте сайт и почту; MAX сам не включается.
5. При сбое: не запускайте службы вручную; пришлите ОБЕЗЛИЧЕННО: фазу (`cat <recovery>/phase`), `failure.txt`, `phases.log`, код выхода. Архивы, `.env`, ключи и дампы не отправлять.

Для пункта 1 (Mac): запускать из проверенных исходников `deploy/recovery/recover-mac.sh <ожидаемый SHA-256>`. Скрипт печатает среду (архитектура, память Docker), отказывает при памяти Docker меньше 1536 МиБ или копии больше 512 МиБ (границы выведены из лимитов самого скрипта: 512m + 512m + запас; tmpfs /tmp 2 ГиБ; это не установленная причина прежнего отказа) и при сбое печатает код выхода контейнера (137 - признак принудительного завершения, возможно по памяти; причина не установлена). Пришлите только этапы, коды и типы ошибок.

## 4. Остаточные риски и внешние блокеры
- Причина отказа восстановления реальной копии на Mac не установлена; без вывода владельца кандидат не может считаться готовым к боевой установке.
- Реальные Docker Compose, PostgreSQL 17, VPS, MAX, webhook, HTTPS и Яндекс Диск в этой среде не проверялись. Оценка места использует измерения живых служб, которые проверены только на имитациях.
- Не изменён более ранний недостаток: установщик не может защитить себя от подмены собственного файла (нужна проверка до запуска).
- `.git` существующего дерева не переносится в новое и остаётся в `recovery/tree` (поведение прежнего переключения дерева).
- Список известных путей прошлых выпусков - реконструкция по Git; при расхождении установщик безопасно откажет.
- Каталог recovery хранит `.env` и копию дерева без шифрования; очистка только ручная.
